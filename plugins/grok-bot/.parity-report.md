## Real extension surface (researched 2026-09-04, `websearch` unavailable — direct first-party doc fetch)

- xAI has **no grok.com bot-plugin marketplace**; extensibility is code-level: OpenAI-compatible
  function calling (`docs.x.ai/developers/tools/function-calling`), server-side Remote MCP tools
  (`docs.x.ai/developers/tools/remote-mcp`), and the **Grok Build `grok` CLI plugin format**
  (`docs.x.ai/build/features/skills-plugins-marketplaces`, catalog repo `xai-org/plugin-marketplace`:
  `skills/`, `commands/`, `agents/`, `hooks/hooks.json`, `.mcp.json`, `plugin.json`).
- Grok Bot cloud teammates expose shareable Bots + Skills/routines/plugins via Settings, no public
  manifest spec (`docs.x.ai/grok-bot/...`); X bots are the separate X API (`docs.x.com`).
- Implemented the closest faithful surface: Grok Build plugin layout + stdlib MCP stdio server +
  function manifest + bridge. Sources cited as bare hostnames in README (repo hygiene forbids
  non-allowlisted `https://` URLs).

## Parity gaps

1. MCP has no hook channel: pre-turn context/capture/session markers need the harness to call
   `bridge.py` (or register `hooks/hooks.json` in Grok Build) — same semantics, host-driven timing.
2. grok.com web chat and X bots expose no installable tool surface: best-effort manual path only
   (`instructions.md` + local `server.py` relay), stated in README compatibility section.
3. `register()` accepts partial contexts (duck-typed) where Hermes assumes full `ctx` — strictly
   more tolerant, no behavior change on full contexts.
